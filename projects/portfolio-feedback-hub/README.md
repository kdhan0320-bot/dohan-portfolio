# 품의선 — 구매 요청부터 결재·발주까지

품의 서류와 담당자를 잇는 결재선에서 이름을 정했습니다. 기존 고른시선의 공개 주소를 유지하고, 구매·총무 담당자의 요청 정리 → 팀장 결재 → 사장님 결재 → 발주 준비 흐름으로 전환했습니다.

- 공개 주소: https://kdhan0320-bot.github.io/dohan-portfolio/portfolio-feedback-hub/
- 범위: 이 앱만 변경. 공통 포트폴리오·갈피록 등 다른 작품은 별도입니다.
- **샘플 기반 프런트엔드 시연**입니다. 실제 AI, 로그인, 결재 서버, 메일·업체 발주는 연결하지 않습니다.
- 자료는 이 브라우저의 localStorage에 저장됩니다. 한 탭에서 시연하며 실제 업무 자료·개인정보를 입력하지 않습니다. 브라우저 자료 삭제 시 사라지고 다른 기기와 공유되지 않습니다.

## 실무 경험과 핵심 문제

사용자가 실제로 설명한 흐름은 엑셀·메일로 요청 내용을 다루고 직접 확인 → 종이 결재 서류 작성 → 팀장 승인 → 사장님 결재 → 본인이 업체에 발주 내용을 전달하는 과정입니다. 화면은 그 사이를 연결하는 구매 담당자를 중심으로 설계했습니다.

복잡한 양식, 불투명한 결재 현황, 중복 구매 가능성은 사용자가 제시한 문제입니다. 발생 빈도·금전 손실·처리 시간은 조사하거나 측정하지 않았습니다. ‘처리 시간 40% 단축’은 검증된 성과로 사용하지 않습니다.

| 핵심 문제(Pain Point) | 설계 규칙(Rule) | 화면과 동작 |
|---|---|---|
| 요청 내용을 결재 서류에 반복 입력 | 원문을 남기고, 확인한 정보는 다음 단계에 재사용 | 원문 → 요청서 초안 → 사람이 검토 → 승인된 내용의 발주 문안 |

| 같은 물품을 다시 구매할 가능성 | 진행 중인 같은 품목을 알리되 자동 차단하지 않음 | 품목명 일치 기록의 규격·수량·목적 비교와 확인 항목 |

## 화면 구성

- `#/`: 역할별 처리 대기·결재 현황. 실제 업무 목록을 먼저, 업무 흐름 안내를 아래에 배치합니다.
- `#/requests`: 제목·품목·번호·거래처 검색, 상태 필터. 상세에서 돌아와도 검색 조건을 유지합니다.
- `#/requests/new`, `#/requests/:id/edit`: 요청 원문과 입력 폼. 필수 정보·정수 수량·단가·날짜 검증, 임시 저장, 제출 전 직접 확인.
- `#/requests/:id`: 요청서, 현재 담당, 결재 이력, 제출본, 승인된 발주 문안.
- `#/approvals`: 팀장·사장님 결재 진행 목록. 현재 결재 차례의 역할만 승인·보완·반려 처리.
- `#/orders`: 발주 관리. 최종 승인 후 발주 준비와 완료 기록.
- `#/about`: 실무 경험, 문제와 설계 규칙, 시연 방법·한계.
- 예전 팁·사례·점검 경로는 새 업무 현황으로 연결합니다. 나머지 잘못된 주소에는 복귀 링크를 제공합니다.

## AI 시연과 제약

- ‘원문으로 초안 만들기’는 **규칙 기반 텍스트 추출**입니다. LLM 호출·문서 업로드·OCR은 없습니다.
- 품목·규격·수량·단가·거래처·사유처럼 원문에 명시된 값만 읽습니다. 알 수 없는 값은 비우고 사용자가 확인합니다. 이미 입력한 내용을 바꾸기 전 확인합니다.
- 합계·필수 값·중복 후보·상태 변경은 일반 코드로 처리합니다. 모델이 결재하거나 주문하지 않습니다.
- 역할 전환은 인증이 아닙니다. 실제 서비스에는 서버 권한 확인·DB·다중 사용자 처리·변경 불가능한 감사 기록·AI 출력 검증이 필요합니다.
- 승인·발주는 브라우저 내 샘플 상태 변경이며, 복사되는 문안에도 실제 발주가 아니라는 표시를 넣습니다.
- 이전 인증·게시글 코드는 삭제하지 않았지만 새 진입점에서 불러오지 않습니다. 이 회차에 기존 비공개 인증·DB 기능은 검증하지 않았습니다.

## 판단 순서·결재선 마감 — 2026-10-30

- 사용자 피드백과 직접 화면 관찰: 모바일 승인 버튼이 품목·금액보다 먼저 보였고, 큰 현황 카드가 첫 처리 요청을 밀어냈습니다. 밝은 메뉴·카드 구성은 갈피록과 비슷한 인상을 주었습니다.
- 규칙: 요청서의 품목·총액·사유 → 중복 후보·원문 근거 → 결정 순서. 발주 기록은 승인된 문안을 확인한 뒤에 둡니다. 별도 확인 체크를 늘리거나 자동 승인하지 않았습니다.
- 보완·승인 후 수정 이력은 `검토한 차수 → 다음 작성 차수`로 표시합니다. 신규 이벤트에는 실제 검토 차수와 다음 차수를 분리해서 보관합니다. 기존 브라우저 자료는 초기화하지 않으며 이전 방식의 보완 이벤트를 화면에서 해석해 표시합니다.
- 현황 숫자를 짧은 요약으로 줄이고 요청명·금액의 글자 위계를 강화했습니다. 직접 측정한 390×844에서 첫 처리 요청의 시작/끝은 약 551/688px였습니다. 이전 검토의 시작/끝은 약 757/892px였습니다. 이는 배치 측정이며 업무 시간 개선 수치가 아닙니다.
- 초안 생성 후 원문은 접히고 요청서로 이동합니다. 원문에서 읽은 값·제목 구성·직접 입력 필요·사용자 수정 값을 구분합니다. 출처 표시는 현재 작성 화면의 보조 정보이며 AI 신뢰도 점수가 아닙니다. 샘플은 가상의 요청 메일 형식이며 납기일처럼 없는 정보는 채우지 않습니다.
- 발주/결재 목록에서 상세를 열면 선택 메뉴와 복귀 경로를 유지합니다. 검색·필터를 포함한 원래 목록으로 돌아갑니다. 기존 ‘발주 준비으로’ 문구는 ‘발주 준비 목록’으로 정리했습니다.

## 재결재 비교·역할 인계 마감 — 2026-10-31

- 문제: 차수만으로는 다시 판단할 변경 내용을 알기 어렵습니다. 규칙: 바로 앞 제출본과 비교해 바뀐 항목만 표시합니다. 작성 화면과 상세에 같은 비교 표를 사용하고, 모바일은 항목 아래 이전·현재 값을 나란히 보여줍니다. 납기·거래처·사유·규격·수량·단가·추가/제외 품목·합계를 비교하며, 품목 순서와 숫자 입력 형식만 달라진 경우는 제외합니다. 저장된 제출본은 바꾸지 않고 이전 기록이 없으면 비교 불가로 표시합니다.
- 문제: 모바일에서 다음 역할로 이어가려면 상단을 찾아야 했습니다. 규칙: ‘시연 역할’을 항상 보이게 하고 요청서의 ‘다음 할 일’에서 현재 담당 역할로 전환합니다. 요청·차수·읽던 위치를 유지하며 역할 전환이 승인까지 실행하지는 않습니다. 최종 승인 후에는 새 발주 문안으로 키보드 초점을 안내합니다.
- 결재함은 팀장·사장님에게 ‘내 차례’를 기본으로 보여줍니다. 직접 선택한 전체/단계 필터와 검색어는 상세 왕복 후에도 유지합니다. 역할을 바꾼 뒤에도 작성 중 미저장 내용의 이탈 확인을 유지합니다.
